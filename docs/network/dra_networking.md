# Attaching Network Devices with Dynamic Resource Allocation (DRA)

**FEATURE STATE:** v1.10.0: Beta

KubeVirt can attach a network device to a virtual machine through Kubernetes [Dynamic Resource Allocation (DRA)](https://kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/).
With DRA, a network device is requested through the Kubernetes `ResourceClaim` API, allocated by the DRA driver, and wired into the VM using a [network binding plugin](network_binding_plugins.md).

The VM interface references the device through a new `resourceClaim` network source.
KubeVirt orchestrates the wiring: the DRA driver provisions the device, and the network binding plugin configures the corresponding interface in the domain.

!!! Note
    This flow always pairs a `resourceClaim` network with a network binding plugin.
    The DRA driver provisions the device; the binding plugin is responsible for configuring the domain interface.
    Writing or deploying a DRA driver or a binding plugin sidecar is outside the scope of this guide — see [Network Binding Plugins](network_binding_plugins.md) and treat the DRA driver as an external dependency.

## Feature gate

The `NetworkDevicesWithDRA` feature gate must be enabled on the KubeVirt CR to use the `resourceClaim` network source.

See [Activating feature gates](../cluster_admin/activating_feature_gates.md) to enable it.

## Prerequisites

- **Network device DRA driver.** An external DRA driver for the target network-device type must be deployed in the cluster. The driver is selected and managed outside of KubeVirt.

- **A `DeviceClass`.** A `DeviceClass` is an admin-defined category of devices. It must exist for `ResourceClaim`/`ResourceClaimTemplate` objects to reference.

- **A registered network binding plugin.** The binding plugin that configures the DRA-backed interface must be registered in the KubeVirt CR. See [Network Binding Plugins](network_binding_plugins.md) for how a cluster admin registers one.

!!! Note "Kubernetes version"
    KubeVirt v1.10 supports Kubernetes 1.35–1.37. Binding plugin support for DRA network devices is available on all of these versions (DRA structured parameters has been GA since Kubernetes 1.34).
    DRA drivers that publish device metadata require **Kubernetes 1.36 or later**.

## Admin vs user responsibility

The DRA network flow splits across two roles:

- **Cluster admin** owns the DRA driver (or operator) deployment and the `DeviceClass` definitions.
- **VM owner (user)** owns the `ResourceClaim`/`ResourceClaimTemplate` provisioning and policy, and the VM interface/network wiring that selects the claim and request references.

## Worked example

The example below requests a network device through a `ResourceClaimTemplate`, then attaches it to a VM.
It assumes a cluster admin has already registered the binding plugin `my-binding-plugin` in the KubeVirt CR — see [Network Binding Plugins](network_binding_plugins.md) for how to register one.

First, create a `ResourceClaimTemplate` that requests a device from the DRA driver:

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: network-claim-template
spec:
  spec:
    devices:
      requests:
      - name: dev
        exactly:
          deviceClassName: my-device-class
```

Then create a VM that references the claim template in `spec.template.spec.resourceClaims`, declares an interface that uses the binding plugin, and adds a network with a `resourceClaim` source that points at the claim and request:

```yaml
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-dra-binding-plugin
spec:
  template:
    spec:
      domain:
        devices:
          interfaces:
          - name: dra-net
            binding:
              name: my-binding-plugin
      networks:
      - name: dra-net
        resourceClaim:
          claimName: network-claim
          requestName: dev
      resourceClaims:
      - name: network-claim
        resourceClaimTemplateName: network-claim-template
```

The following pod is generated by `virt-controller` from the VM above.

```yaml
---
apiVersion: v1
kind: Pod
metadata:
  name: virt-launcher-vmi-dra-binding-plugin
spec:
  containers:
  - name: compute
    image: virt-launcher
    resources:
      claims:
      - name: network-claim
        request: dev
  - name: my-binding-plugin
    image: my-binding-plugin-sidecar:latest
    resources:
      claims:
      - name: network-claim
        request: dev
  resourceClaims:
  - name: network-claim
    resourceClaimTemplateName: network-claim-template
```

!!! warning "Important"
    **These fields must reference each other:**

    - `spec.template.spec.resourceClaims[].resourceClaimTemplateName` must match the `metadata.name` of the `ResourceClaimTemplate` (`network-claim-template` in this example).
    - `spec.template.spec.networks[].resourceClaim.claimName` must match `spec.template.spec.resourceClaims[].name` for the claim that backs the device (`network-claim` in this example).
    - `spec.template.spec.networks[].resourceClaim.requestName` must match the request `name` defined in the `ResourceClaimTemplate` (`dev` in this example).

    The interface and the network are correlated by their shared `name` (`dra-net` in this example), exactly like any other KubeVirt interface/network pair.

## Validation rules

KubeVirt validates DRA network configuration when the VM/VMI is created. Your configuration must satisfy all of the following:

- An interface mapped to a `resourceClaim` network **must** use a network binding plugin.
- Both `claimName` and `requestName` must be set (non-empty).
- The `claimName` + `requestName` tuple must be **unique** across all networks, `hostDevices`, and `gpus` — no two entries may share the same claim and request.
- `multus` and `resourceClaim` network sources **cannot** be mixed in the same VMI.

## Known limitations

- **MAC address and interface name cannot be set through the DRA flow.** The MAC is determined by the driver/plugin contract, and the guest-visible interface name is determined by libvirt/QEMU.
- **Live migration** is supported only for `resourceClaimTemplate`-backed claims, not for a direct `resourceClaim` reference.
- **One device per request.** If a request allocates more than one device (`count > 1`), only the first allocated device is used.
